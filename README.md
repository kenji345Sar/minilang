# minilang

文字列で書かれたプログラムを解釈して動かす、小さな言語処理系。**言語処理（コンピュータが書かれた言葉を理解して動かす仕組み）を、自分の手で書きながら理解する**ことが目的。

## 言語処理とは何か

`1 + 2 * 3` という文字列を受け取って `7` を返す、これを実現するために裏で起きていることを3段に分けて、自分で書く。

### 暗算で考える

あなたが `1 + 2 * 3` を暗算するとき、頭の中で無意識にこの3段をやっている：

1. **読む**：「1」「+」「2」「*」「3」と単語に切り分ける
2. **構造を理解する**：「`*` は `+` より先に計算する」と関係を組み立てる
3. **計算する**：`2*3=6`、`1+6=7`

このリポジトリは、この3段をそのまま Python で書いたもの。

| 段 | 入力 | 出力 | 担当ファイル |
|---|---|---|---|
| Lexer | 文字列 `"1+2*3"` | トークン列 `[1, +, 2, *, 3]` | `lexer.py` |
| Parser | トークン列 | 構文木 `BinOp(+, 1, BinOp(*, 2, 3))` | `parser.py` |
| Evaluator | 構文木 | 値 `7` | `evaluator.py` |

`main.py` はこの3段を順に呼び出して REPL を回しているだけ。

### 段と段がどう協力するか — 優先順位の例

「`*` は `+` より先に計算する」というルールは、Parser と Evaluator に**分担**されている。

- **Parser が判断する**：木を組み立てる段階で「`*` を内側、`+` を外側」に配置する
- **Evaluator は実行するだけ**：再帰で木を辿る。葉から戻ってくる順に評価するので、内側の `*` から先に計算される

```
       BinOp(+)         ← 外側
       /     \
      1     BinOp(*)    ← 内側 → 先に計算される
             /    \
            2      3
```

優先順位の**判断**（Parser）と**実行**（Evaluator）が違う段に分かれているので、Parser が一度形を決めれば Evaluator は何も考えずに辿るだけでいい。3段に分けた一番のご利益はここ。

（`(1+2)*3` のように括弧で順番を変えると、Parser が組み立てる木の形が変わる。Evaluator のコードは1行も変えなくていい。）

### コードでどう実現しているか — `_expr` と `_term` のネスト

Parser の中身は `_expr`（`+` `-` を扱う）と `_term`（`*` `/` を扱う）という2つの関数に分かれている。**`_expr` は左右のオペランドを取るときに `_term` を呼ぶ**、というネスト構造が優先順位を作っている。

`1 + 2 * 3` を読むときの流れ：

| ステップ | 動き |
|---|---|
| 1 | `_expr` が呼ばれる。まず**左**を取るため `_term` を呼ぶ |
| 2 | `_term` は `1` を読む。次のトークンは `+` で `*` `/` ではないので、`Num(1)` だけ返す |
| 3 | `_expr` は `+` を消費し、**右**を取るためまた `_term` を呼ぶ |
| 4 | `_term` は `2` を読む。次が `*` なので吸い込み、`3` まで読んで `BinOp("*", 2, 3)` を作って返す |
| 5 | `_expr` が `BinOp("+", 1, BinOp("*", 2, 3))` を組み立てて完成 |

**鍵は `_term` の `while` ループが `STAR` と `SLASH` だけを条件にしている**こと（[parser.py:74](parser.py#L74)）。`_term` は `*` `/` を吸い込んでから返してくる。だから `*` を含む部分は必ず `+` の**オペランドの中身**として木の内側に入る。もし `_term` が `+` も吸ったら優先順位が壊れる。

```python
def _expr(self) -> Node:
    node = self._term()              # 左：_term が * を吸ってから返す
    while self._peek().kind in (TokenKind.PLUS, TokenKind.MINUS):
        op = "+" if ... else "-"
        node = BinOp(op, node, self._term())  # 右：また _term を呼ぶ
    return node

def _term(self) -> Node:
    node = self._factor()
    while self._peek().kind in (TokenKind.STAR, TokenKind.SLASH):  # ★ ここ
        op = "*" if ... else "/"
        node = BinOp(op, node, self._factor())
    return node
```

「呼び出すと結果が深くなる」ことで、**呼び出し関係の深さ＝木の深さ＝計算の先後**が一致する仕組みになっている。

該当：[parser.py:65-77](parser.py#L65-L77)

## なぜ自分で書くのか — Python の `eval()` でいいのでは？

Python には `eval("1+2*3")` という、文字列を渡せば `7` を返す機能が組み込まれている。だから**電卓の答えを得るだけ**なら自分で書く必要はない。

このリポジトリの目的は答えを得ることではなく、**`eval()` の中で起きていることを自分で書いて理解する**こと。

| | Python の `eval()` | このリポジトリ |
|---|---|---|
| 計算結果を得る | できる | できる |
| Lexer / Parser / Evaluator の中身 | 見えない（ブラックボックス） | 自分で書くので全部見える |
| 言語を拡張できる | できない（Python の文法に縛られる） | できる（step 3 で `if`、step 4 で関数を足す） |
| 安全性 | 外部入力に対して危険（任意コード実行） | 自分で書いた範囲しか動かない |

つまり step 1 だけ見ると `eval()` と同じ機能しか作っていない。これは「土台を組む段階」だから。step 3 以降、`eval()` では作れない言語機能を足すときにこの土台が活きる。

## ステップ

各ステップは「前のステップで足りなかったもの」を1つずつ足す構成。

| | 扱う単位 | できること | 内部で増えるもの |
|---|---|---|---|
| Step 1 | 式 1個 | 四則演算と括弧を評価 | 3段の枠組み |
| Step 2 | 文の並び | 変数に値を保持、`print` で出力 | 環境 `env`、文（statement） |
| Step 3 | 文の並び | `if` / `while` で分岐・反復 | 制御フローのノード |
| Step 4 | 文の並び | 関数定義と呼び出し（クロージャ） | スコープ・第一級関数 |

各ステップの実装詳細は `docs/stepN.md`。

## 動かす

```
cd minilang
python3 main.py
```

REPL が起動する。`exit` または `quit` で終了。

```
> 1 + 2 * 3
7
> x = 10;
> y = x * 4;
> print(y);
40
```

## 過去ステップのコードを読む

トップレベルの .py は常に**今のステップ**のコード。過去のステップは `snapshots/stepN/` にスナップショットがある。

```
cat snapshots/step1/main.py       # step 1 の REPL
cat snapshots/step1/evaluator.py  # step 1 の評価器
```

`git checkout` は不要。トップレベルと `snapshots/` を並べて見られる。
